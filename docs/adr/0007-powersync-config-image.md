# Bake PowerSync's config.yaml/sync-rules.yaml into a custom-built image instead of hand-copying files onto the prod host

The prod host ran PowerSync off `journeyapps/powersync-service:latest` with `config.yaml`/`sync-rules.yaml` bind-mounted from hand-copied files, not a git checkout — nothing kept them in sync with this repo. That already caused a real, silent bug: a deploy missed the `image` sync rule and photos never synced, with no error anywhere. The fix is to extend the existing backend-image release pipeline (`.github/workflows/backend-image.yml`) with a sibling workflow, `powersync-image.yml`, that builds `powersync/Dockerfile` (`FROM journeyapps/powersync-service` + `COPY config.yaml sync-rules.yaml /config/`) and publishes `ghcr.io/mathiazom/innbo-powersync` on the same release/push/workflow_dispatch triggers and tag scheme as the backend image. `docker-compose.prod.example.yml` now pulls that image with the same `${IMAGE_TAG}` var the backend service already uses — one release cuts both images, one var to bump on the host — and drops the `./powersync:/config:ro` bind mount entirely. This rides the deploy step that already exists and is already documented ("pull the new image and `docker compose up -d`"), so there's no new manual step and no new host-side git checkout to maintain. Dev's `docker-compose.yml` is untouched, still bind-mounting `./powersync` directly for fast local iteration on sync rules without a rebuild — the drift problem never existed there.

Two alternatives were considered and rejected. Cloning this repo onto the prod host and pointing the bind mount at that checkout (BACKLOG.md's original candidate) works, but adds a new manual `git pull` step to what is otherwise a purely image-pull-based deploy — more for a single self-hoster to remember, not less. Baking the config into the existing `innbo-backend` image instead of a separate `innbo-powersync` image was also considered, but that means merging two different runtimes (a compiled Go binary and the third-party Node-based `powersync-service`) into one container/process — via a multi-runtime image and a process supervisor — which breaks the ability to restart PowerSync alone to pick up a sync-rules change without also bouncing the backend and killing in-flight requests, and couples upstream PowerSync releases to this project's own release cadence. `docker-compose.yml`'s remaining hand-maintained bits (the reverse-proxy network block, etc.) are a separate, still-accepted drift risk — out of scope here since they're inherently host-specific and can't come from a template.
