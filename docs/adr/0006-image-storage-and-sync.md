# Image metadata syncs through PowerSync like any other row; only the binary bytes get a custom HTTP API

PowerSync syncs SQLite rows, not files, so an `image` row (item_id, created_at) and its actual photo bytes need two different transports. Rather than inventing a bespoke protocol for both, the `image` row is a normal synced `Table` — like `room`/`item` — going through the existing `/upload` CRUD-sink and `allowedColumns` whitelist (`backend/internal/httpapi/upload.go`), so every device learns an image exists the same way it learns about anything else. Only the bytes get new endpoints: `PUT /images/{id}` and `GET /images/{id}/full|thumbnail` (`backend/internal/httpapi/images.go`), reusing the same bearer-JWT device auth as every other endpoint. Files are stored and served keyed by the row's own id (`<storageDir>/<id>/{full,thumb}`, no extension) — Flutter's `Image.file` and Go's `http.ServeContent` both determine image format from content, not filename, so no `file_name`/`content_type` column is needed on the synced row.

Two consequences of splitting the transport this way, both accepted rather than engineered around: the client generates the row's id locally and may `PUT` its bytes before that row's own sync reaches Postgres (metadata sync is async relative to the immediate upload attempt) — the upload handler accepts bytes unconditionally under the authenticated device's id instead of checking for the row first, so an orphaned blob (row never arrives) is possible but harmless, consistent with ADR-0003's already-accepted best-effort character. And thumbnails are generated server-side (`github.com/disintegration/imaging`) rather than client-side, so decoding doubles as upload validation and no image-processing dependency is needed in the Flutter client. That same decode step applies the photo's EXIF orientation (phones commonly store portrait photos as landscape pixel data plus a rotation tag) and re-encodes *both* the thumbnail and the full-res copy with it already baked in, rather than storing the original bytes verbatim — cross-device testing showed EXIF-orientation handling isn't consistent enough across image renderers to rely on every client interpreting the tag the same way, so normalizing once server-side means every consumer just sees already-correct pixels. `has_full_local` (from the plan doc's original data model sketch) is deliberately *not* a column on the synced row — it's inherently per-device state, so each device answers "do I have the full-res file?" via local file existence instead, same as any other local-only concern. Deleting an `image` row's blob happens in the same CRUD-delete handler that removes the Postgres row, once the delete transaction commits — one place, no separate cleanup job, matching the transactional-adjacent shape the handler already had.
